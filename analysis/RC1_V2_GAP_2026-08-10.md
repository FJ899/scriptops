## 3. Concrete blockers in the existing happy path

These are not speculative feature requests; they prevent a clean run from command/task to approved Git change.

### B1 — task creation conflicts with clean-tree preflight

`cmd_review` writes `tasks/<TASK>/task-pack.yaml` but does not commit it. `cmd_check_pre` immediately checks `git_is_clean()` and fails when the newly created task is uncommitted.

Therefore the advertised sequence `review → check-pre` is not self-consistent without an undocumented manual Git commit.

### B2 — intermediate evidence leaves the tree dirty before approval

`check-pre` writes validation and prompt-ready artifacts. `context-build` writes the context pack. A manually supplied `webai-output.md` is also an uncommitted task artifact. `check-post` commits only the staged candidate and validation report.

`cmd_approve` begins with `ensure_git_clean()`. Unless a human manually commits the omitted task/evidence artifacts between commands, approval is blocked by the tool's own generated files.

### B3 — accepted scene hash becomes stale

`cmd_approve` reads the candidate text and performs a text replacement from `status: candidate` to `status: accepted`, then writes the file directly. It does not recompute the scene front-matter `hash` after that content change.

The decision-log `artifact_hash` hashes the final text, but the scene's own declared hash still describes the candidate form. The accepted canonical artifact is therefore internally inconsistent.

### B4 — human approval lacks required rationale

`approve` takes only `--scene`. The decision record contains the approver and artifact hash but no mandatory `why`, contrary to the current RC1 contract.

### B5 — no impact artifact before human decision

The requested loop contains `impact report → human decision`. v2 has no impact-report command or persisted impact artifact.

## 4. Smallest implementation slice for one successful use case

If v2 is selected as the implementation base, the minimum delta for **one approved happy-path case** should reuse the single-file prototype rather than build a new system.

Required for that one path:

1. make task creation produce a durable/clean checkpoint compatible with `check-pre`;
2. define clean Git lifecycle for generated task/context/candidate evidence so `approve` is reachable without undocumented manual commits;
3. persist a minimal impact report after successful post-validation;
4. require `approve --why <text>` and write the rationale into the decision record;
5. recompute the accepted scene hash after changing status to `accepted`;
6. add one deterministic smoke test in a temporary Git repository covering the exact successful sequence.

Not required for this first successful case and therefore not proposed in this slice:

- browser helper or model API;
- autonomous AI approval;
- dashboard/GUI;
- vector database or semantic graph;
- multi-user;
- cloud sync;
- generalized agent framework;
- SQLite, unless the smoke path proves plain files are insufficient;
- reject/revision UX, unless the first happy-path test cannot be isolated without it.

The last two items remain part of broader RC1 requirements, but they do not need to block proof of one successful approved path.

## 5. Recommendation and decision boundary

Engineering recommendation: **use `legacy/scriptops-v2-single.py` as the base for the first one-case repair slice**, because it already contains the CLI, Git, task/context, validation, staging, approval and decision-log mechanics. Rewriting those mechanisms would add scope without closing a demonstrated blocker.

This document does not promote that recommendation into project truth. Per `DEC-SO-006` and `DEC-SO-007`, base selection remains the next semantic decision before implementation.
